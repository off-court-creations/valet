## CSS-in-JS style engine (src/css + src/system style integration) — 83/100

The valet style engine is one of the most mature, best-tested subsystems in the repo and its public API (styled, keyframes, definePreset, preset) is genuinely ready to freeze. It is small, dependency-free, and deterministic: class names are FNV-1a hashes of normalized CSS (src/css/hash.ts, src/css/normalize.ts) with pinned hash vectors incl. UTF-8 boundary/astral cases. Render is pure — class names compute synchronously in render (SSR-safe) while CSSOM writes are queued and flushed from useInsertionEffect (createStyled.ts:269-277), giving StrictMode/concurrent safety and first-paint correctness, all proven by a render-phase probe in createStyled.dom.test.tsx. Atomic dedup + never-re-inject, a 2-layer memo (global LRU 4096 + per-instance last-raw ref), a globalThis Symbol.for registry for bundler-duplication safety, dev hash-collision + rule-cardinality tripwires, and doubled-selector preset specificity are all implemented and tested (163 engine/precedence/renderCount tests pass; the 29-agent foundation audit verified the engine with zero blockers). The two real reservations are capability gaps, not API defects: (1) there is no SSR style-collection API, so server-rendered HTML carries deterministic class names but no rules → FOUC/CLS until the client hydrates (disclosed in README, hurts W/A); and (2) the immortal-rule design plus a dev-only cardinality tripwire means a consumer baking continuous values into rule text (an R3F HUD over a rAF loop, the G lens) leaks unbounded CSSOM rules in production with no warning or cleanup. Both are additive/documentable and do not block freezing the existing engine surface.

#### 1. No SSR style-collection API — server HTML ships class names but zero component CSS (FOUC/CLS until hydration)

In Node the engine records rules into pendingRules (sheet.ts:153-160) but renderToString never serializes them, and useInsertionEffect does not run on the server, so flushRules never fires server-side. styles.css ships ONLY token fallbacks (bg/text/space/radius/fonts) — no component/layout rules. README.md:75 explicitly: 'SSR: not yet … no getServerStyles-style call … first paint can flash unstyled before the client hydrates'. foundation-audit-2026-06-18.md:46-48 records the decision 'No action for 1.0'.

But it caps confidence for two of the four downstream lenses: W (marketing SSR/SSG gets unstyled first paint, slow LCP of styled content, layout shift) and A (ad landing pages where CLS/LCP directly drive conversion and quality score). 1.0 should ship with this position made explicit (carve SSR-extraction out of the SemVer guarantee in README/VERSIONING) so adopters are not surprised, rather than leaving it only in a prose README line.

#### 2. Immortal-rule cardinality guard is dev-only — continuous interpolations leak unbounded CSSOM rules in production (the R3F/rAF footgun)

- **Claimed severity:** 🟡 medium · **Effort:** M
- **Evidence:** Rules are never deleted (createStyled.ts:59-68; the only deleteRule is the preset in-place theme swap at stylePresets.ts:87). The styled() and keyframes() cardinality tripwires are nulled in production: mintedKeyframes (createStyled.ts:79-80) and mintedClasses (createStyled.ts:201-202) are both `process.env.NODE_ENV === 'production' ? null : new Set()`, and the warn path bails when the set is null. So a styled`width:${p=>p.$pct}%` (or keyframes body) driven by a continuously-varying value mints one permanent rule per unique value with zero warning in prod and no cleanup.
- **Why it gates 1.0:** Strongly informs the highest-risk lens (G): an R3F HUD/overlay that interpolates a live game value (health %, timer, transform) into a styled template inside a requestAnimationFrame-driven re-render will grow the CSSOM every frame, progressively slowing style recalculation over a session — a production memory/perf leak a consumer only learns about in dev. The design is intentional and documented (AGENTS.md rule-lifecycle policy; valet's own components route continuous values through CSS vars), so this is not a correctness bug and not a hard freeze blocker, but 1.0 should ship a production-observable guard or prominent G/D-targeted docs since the engine API is about to freeze around this contract.

### Capability gaps

- **No server-side critical-CSS extraction / per-request style boundary** _(affects: W, A)_ — The registry is process-global and deterministic (safe for concurrent SSR), but there is no public API to collect the CSS generated during a renderToString pass and inline it into the response, and no per-request reset. styles.css covers only design tokens, so 'styled, fast first paint without JS' is limited to token theming; all component layout/visuals require client hydration. `sheet.ts:153-160 (pendingRules recording, never serialized to HTML); styles.css (tokens only); README.md:75 (disclosed roadmap item).`
- **Immortal rules + no production cardinality guard for live/continuous values** _(affects: G, D)_ — Atomic rules are never freed (by design). Continuous or high-frequency interpolations baked into rule text grow the CSSOM unbounded; the only safety net (dev cardinality tripwire, limit 256) is compiled out in production. Affects rAF-driven overlays and live-updating data the most. `createStyled.ts:59-69, :79-80, :201-202; stylePresets.ts:87 is the only deleteRule.`
- **styled() targets intrinsic tags only — no styled(Component) composition** _(affects: all)_ — The factory is constrained to keyof JSX.IntrinsicElements, so you cannot pre-style an existing component the way Emotion/styled-components allow. The `as` prop covers per-call-site polymorphism but not reusable composition. Additive to add later, but a DX gap teams hitting from those libraries will notice. `createStyled.ts:156 (styled<Tag extends keyof JSX.IntrinsicElements>); `as?: React.ElementType` at createStyled.ts:186-193.`
- **Unlayered cascade — no @layer integration** _(affects: W, D)_ — Engine rules are inserted unlayered and rely on single-class (0-1-0) specificity, with presets using a doubled selector to win ties. Deliberate (stylePresets.ts:13-22 explains why @layer was rejected), but consumers interleaving their own design-system CSS get insertion-order/specificity coupling rather than explicit layering. `stylePresets.ts:13-22 (Why-not-@layer rationale); sheet.ts:135-145 (append at cssRules.length).`

### Strengths (don't over-fix)

- Render purity is real and tested: class names compute synchronously in render (SSR/renderToString works) while CSSOM mutation is deferred to useInsertionEffect, which runs before layout effects/paint — proven by the render-phase probe asserting zero insertRule calls during render yet live computed styles in a layout effect (createStyled.dom.test.tsx:153-199; createStyled.ts:269-277).
- Deterministic hashing with a frozen contract: FNV-1a 64-bit + base36 length suffix, pinned default+unicode vectors covering every UTF-8 width boundary and astral input, plus seed-override determinism (hash.ts; hash.test.ts, 19 cases). Independent styled() definitions of identical CSS agree on the class across separate Node processes (ssr-import.test.ts).
- Atomic dedup + never-re-inject is airtight across re-render, unmount/remount, independent roots, StrictMode double-render, and prop-flip-and-revert — exactly one insertRule per unique class (createStyled.dom.test.tsx:58-332).
- Bundler-duplication safety: all singleton state lives in a versioned globalThis[Symbol.for('@archway/valet/style-registry/v1')] registry, so two module copies share one cache and one <style> element with no double-injection (sheet.ts:51-91; styleRegistry.test.ts + styleRegistry.dom.test.ts).
- SSR-safe by construction: the CSSStyleSheet is created lazily on first DOM injection (never at module scope), Node records pendingRules deterministically, and the Node→DOM same-process backlog flushes on the first insertion effect (sheet.ts:120-171). Built-dist SSR smoke tests confirm no crash + identical markup across renders (ssr-render.test.ts, ssr-import.test.ts).
- Per-commit overhead under a rAF re-render storm is tiny: flushRules() is an O(1) no-op when nothing is queued, and a 2-layer memo (per-instance last-raw ref + global LRU 4096) skips normalize+hash on repeats — verified via normalize call-count spies (createStyled.dom.test.tsx:237-280).
- normalize.ts is a token-aware scanner (not regex): it preserves bytes inside quoted strings/url()/comments, collapses ;-runs before }, honors escapes, and is idempotent (29 tests) — and class hashes derive from its output, so the cache key is robust.
- Engine public surface is minimal and already locked-down: internal singletons (styleCache/globalSheet/presetHas) are removed from the barrel and asserted gone via negative type-probes (public-api.test-d.ts:90-98) and the engine smoke gate (scripts/checks/engine-smoke.mjs). No TODO/FIXME markers anywhere in src/css.
- Good developer footguns where they matter: dev hash-collision guard (sheet.ts:101-117) and dev cardinality tripwires for both styled() and keyframes() that name the offending template and prescribe the CSS-var fix (createStyled.ts:203-218, :340-357).

- **Evidence:** All three templates declare `"vite": ">=6.4.1"` with no upper bound (templates/ts/package.json:40, templates/hybrid/package.json:40, templates/js/package.json:34) while pinning `@vitejs/plugin-react@^4.4.1`. Vite 7 already exists; `>=6.4.1` will resolve a future major that plugin-react ^4 may not support.
- **Why it gates 1.0:** A 1.0 scaffolder is a long-lived artifact people will run for years; an unbounded build-tool range makes a fresh scaffold's success depend on the registry state of the day rather than something reproducible. Bound it (e.g. `^6.4.1` or `>=6.4.1 <8`) before freezing the 1.0 story.

No image-optimization story is demonstrated (valet has an Image component but no template uses it). `packages/create-valet-app/templates/ts/index.html:1-13`
- **No dashboard / app-shell template** _(affects: D)_ — Every template scaffolds a near-empty Surface + Box + Stack + Typography + Button page. No AppBar/Drawer app-shell, no Table, no density/compact-mode demo, no data-dense or virtualized-list layout — a dashboard author starts from near-zero. (Grep confirms zero AppBar/Drawer/Table/Tabs/Modal usage across templates.) `packages/create-valet-app/templates/ts/src/pages/start/Quickstart.tsx:1-18; grep for AppBar|Drawer|Table|Tabs|Modal in templates/ returns nothing`
- **No minimal/static landing template and no analytics/A-B scaffolding for ad campaigns** _(affects: A)_ — `--minimal` still ships react-router-dom + zustand + the full valet SPA runtime for a single page (bin/create-valet-app.js:807-923 only trims the second route). ### Strengths (don't over-fix)

- All three templates genuinely produce a buildable, preview-able valet app, proven by an honest end-to-end harness that scaffolds every template/flag combo and runs generate→install (published valet)→lint→typecheck→build→preview (scripts/validate.mjs:198-261, 22-76).
- Strong packaging hygiene: scripts/pack.test.mjs guards the exact dangling-bin-symlink regression that previously shipped, and asserts each declared bin resolves, is executable, and appears in `npm pack --dry-run` output.
- Mature consent model for machine-mutating side effects: decideGlobalMCP is a pure, auditable precedence function (bin/create-valet-app.js:1437-1447) and scripts/consent.test.mjs drives the real bin in a sandbox with fake npm/git/code on PATH to prove no global install/config edit happens without explicit opt-in.
- Good first-paint + privacy defaults: fonts are self-hosted via @fontsource with injectRemote:false so there are zero Google Fonts requests (templates/ts/src/main.tsx:9-14, App.tsx:23-32), and theme init defaults to system mode with persistence.
- Forward-looking `--three`/`--r3f` flag exists at all — most design-system scaffolders ship nothing for 3D; this is the right instinct even though the current template is only a demo.
- bump.mjs keeps the CLI fallback version, all three template valet ranges, and the lockfile in sync for minor/major bumps, and correctly produces a 1.x-aware range; the dead docs-path bug flagged in the 1.0 plan (plan.md:175) is already fixed (bump.mjs:113-116).
- Tailored, validated agent guidance: AGENTS.md/CLAUDE.md are rendered per template/flag from a single base and asserted by postChecks (validate.mjs:334-419).

### Recommendations

- **[P0]** Decide the SSR/SSG story for 1.0: ship a marketing/SSG template (Astro or vite-ssr/Next) or explicitly document 'valet runs in your SSR framework' — valet did the SSR-correctness work; close the loop so W/A consumers can actually get server-rendered HTML + SEO meta. If a full template is out of scope for 1.0, add SEO meta (description/OG/canonical/theme-color) to the existing index.html and document the SSR integration path so the gap is a conscious choice, not an omission.
- **[P0]** Add the fast, hermetic packaging gate (scripts/pack.test.mjs) to per-PR CI — It needs no network and runs in seconds; wiring `npm run pack:check` into .github/workflows/ci.yml gives the scaffolder a real per-PR regression gate without the published-valet dependency that keeps full validate on a weekly cron.
- **[P1]** Rework or honestly re-scope the R3F template for the game (G) lens — Make the canvas the primary layer with a valet HUD/menu/modal portalled above it (interactive, pointer-events correct), add a note on keeping valet state out of the useFrame loop, and include @types/three to drop the @ts-expect-error. If kept as-is, rename/label it a 'background-effect demo' so it doesn't imply a game-ready scaffold.
- **[P2]** Bound the vite range and harden the preview check — Replace `">=6.4.1"` with a bounded range across all three templates so a frozen 1.0 scaffold stays reproducible, and extend validate.mjs preview to assert the page renders valet content (DOM contains expected text and no console errors), not just HTTP 200.
- **[P3]** Add a dashboard/app-shell template (D) and a lean static-landing variant (A) — A dashboard template wiring AppBar + Drawer + Table + density/compact, and a router-less/zustand-less static landing template with an analytics hook, would let the scaffolder actually launch all four named products rather than only a generic SPA.
