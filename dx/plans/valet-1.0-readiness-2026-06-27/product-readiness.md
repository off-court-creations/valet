## React-three-fiber video game UI — valet DOM HUD/menus/overlays layered over a live WebGL &lt;canvas&gt; driven by a rAF render loop (G lens).

**Readiness: 65/100**

valet is more ready for a game HUD than its "DOM kit" label suggests, but it ships no game-specific primitive and its screen root fights the over-canvas use case. The CSS-in-JS engine is genuinely rAF-safe: render only computes class names from a cache (createStyled.ts:226-273), all CSSOM mutation is deferred to useInsertionEffect (createStyled.ts:277), there is a two-layer memo, and a dev "rule cardinality" tripwire actively warns when a continuously-varying value leaks an immortal CSS rule (createStyled.ts:69,203-217) — valet's own dynamic values go through inline style instead (ProgressBar, Progress.tsx:186). So valet never injects styles per-frame under correct use, and because it renders only to the DOM tree (outside R3F's &lt;Canvas&gt;) with peer deps limited to react/react-dom/zustand, it coexists cleanly with @react-three/fiber's custom reconciler. Layering is a strength: one TS z-index scale (1050–1600) that is CSS-variable-overridable and exported (zIndex.ts; zVar/VALET_ZINDEX exported in index.ts), repo-enforced against stray literals. The overlay system is solid — body-portal, LIFO stack, Escape, stack-aware outside-click, focus trap/restore (overlay.ts) — and several overlays are deliberately non-locking (Select/Tooltip/SpeedDial/Snackbar use inertBackground:false), so a FAB menu or toast can float over a still-running canvas. The gaps are ergonomic, not correctness: (1) Surface, the mandatory single theme root, is position:fixed/inset:0/opaque/overflow:auto, throws on nesting (Surface.tsx:63), and every component throws without it (surfaceStore.ts:196) — it eats pointer events and visually covers the canvas by default; you must hand-hack background:transparent + pointerEvents:none via sx, undocumented. (2) There is no HUD-layer/Portal/Presence primitive exported and getOverlayRoot/useOverlay are internal, so pointer pass-through and reusable portaling are DIY. (3) Modal hardcodes inertBackground+trapFocus (Modal.tsx:239-241) with no opt-out and returns null on close (no exit animation, Modal.tsx:261). (4) Zero R3F guidance/example; WebGLCanvas exists but is valet's own raw WebGL2 host, irrelevant to an R3F &lt;Canvas&gt;. A competent dev can build a good HUD today via Box+sx escape hatches; nothing is structurally broken, but valet offers no first-class game scaffolding.

### Product blockers

#### 1. No HUD/overlay-layer primitive and no Portal/overlay-root export; Surface eats pointer events by default

- **Claimed severity:** 🟠 high · **Effort:** M
- **Evidence:** src/components/layout/Surface.tsx:229-244 (fixed, opaque, overflow:auto) + :274 (sx is the only escape hatch); src/system/overlay.ts:283-293 getOverlayRoot is internal, not in src/index.ts; no Portal/Presence export (grep of index.ts is empty).
- **Why it gates 1.0:** The single most common game-UI need — DOM HUD that lets clicks/drags fall through to the canvas with interactive islands on top — has no first-class support. Because 1.0 FREEZES the barrel exports, the ergonomic primitive (a transparent/pass-through overlay Surface mode or an exported HUD/Portal layer that joins valet's z-scale + overlay stack) is best shipped in the frozen surface rather than bolted on later. Today it is achievable only by hand-hacking Surface sx, which is undocumented and fights the defaults.

#### 2. Modal cannot run non-blocking over a live game (inertBackground + trapFocus hardcoded, no opt-out)

- **Claimed severity:** 🟡 medium · **Effort:** S
- **Evidence:** src/components/layout/Modal.tsx:239-241 (trapFocus:true, inertBackground:true with no prop); overlay.ts:88 sets body.style.overflow='hidden' and inerts all body siblings including the canvas.
- **Why it gates 1.0:** A game HUD frequently shows a floating panel/dialog that must NOT pause or de-interact the canvas. Modal always locks+inerts the background and traps focus. A `keepBackgroundInteractive`/`modal={false}` prop (mirroring the inertBackground:false overlays Select/SpeedDial already use) closes this. Adding a prop after freeze is additive, but a 'terrific' game story wants it at 1.0.

#### 3. No generic enter/exit presence; Modal has no exit animation

- **Claimed severity:** 🟡 medium · **Effort:** M
- **Evidence:** src/components/layout/Modal.tsx:261 returns null on close (enter-only); Snackbar.tsx:185-235 hand-rolls exit presence; no AnimatePresence/Presence primitive in index.ts.
- **Why it gates 1.0:** HUD/menu polish (slide/fade-out on dismiss) is expected in games. Each component reinventing presence is inconsistent and Modal simply pops out. A small exported presence helper (or at least a mounted-while-exiting Modal) would make HUD transitions feel finished.

#### 4. Zero react-three-fiber guidance, recipe, or example

- **Claimed severity:** 🟡 medium · **Effort:** S
- **Evidence:** docs grep: only WebGLCanvas demo (valet's own GL) and LavaLampBackgroundGL; no R3F/<Canvas>/HUD-over-canvas page in docs/src/pages/concepts (only Events.tsx).
- **Why it gates 1.0:** The over-canvas patterns DO exist (transparent pass-through Surface via sx, zVar interleaving, non-locking SpeedDial/Snackbar, persistent Drawer as side HUD), but a consumer cannot discover them. A single 'valet UI over a WebGL/R3F canvas' concept doc + example would convert a DIY scavenger hunt into a supported path and is the cheapest, highest-leverage fix for this lens.

### Recommendations

- **[P0]** Ship a documented over-canvas pattern before the API freeze: a transparent/pointer-events-pass-through overlay mode (e.g. Surface `overlay`/`transparent` prop or an exported HUD layer) that joins valet's z-scale and overlay stack — Make 'DOM HUD over a live canvas' a first-class, frozen capability instead of an sx hack on an opaque fixed Surface. At minimum, document that <Surface sx={{background:'transparent', pointerEvents:'none'}}> over a fixed/absolute canvas + interactive islands with pointerEvents:'auto' is the supported recipe.
- **[P1]** Add a non-blocking Modal mode (`modal={false}`/`keepBackgroundInteractive`) and give Modal an exit animation — Let HUD dialogs float without inerting/locking the canvas or trapping focus (reuse the inertBackground:false path Select/SpeedDial already use), and keep the dialog mounted for one transition on close so it fades out like Snackbar does.
- **[P1]** Publish an R3F/WebGL concept doc + runnable example — Cover layering a Surface HUD over @react-three/fiber's <Canvas>, z-index interleaving via zVar/--valet-zindex-* overrides, pointer-event pass-through, non-blocking pause menus vs persistent-Drawer side HUDs, and the engine's 'route per-frame values through inline style/CSS vars, never styled template' rule so games never trip the immortal-rule cardinality warning.
- **[P2]** Export a small presence/Portal helper (optional) for reusable HUD enter/exit and custom layers — A minimal exported Presence (mount/unmount with enter/exit classes keyed to theme.motion) and/or a public portal target tied to the overlay stack would let game devs build custom HUD overlays that participate in valet's Escape/outside-click/focus/z-index instead of hand-rolling parallel portals. Best added pre-1.0 since it expands the frozen surface.
- **[P3]** Reconcile the 'everything experimental' status story with the shipped meta (60 stable / 3 experimental) and re-affirm the rule-lifecycle guard — Confirm the HUD-critical components (Modal/Drawer/Tooltip/Snackbar/SpeedDial/Surface/Box/WebGLCanvas) are intentionally 'stable' for 1.0, and keep the createStyled cardinality tripwire (createStyled.ts:203-217) — it is the safety net that keeps a 60fps React-driven HUD from leaking CSS rules.

## Internal dashboards — data-dense tables (sort/select/large data/virtualization), charts/data-viz, dense/compact density mode, complex forms, app-shell navigation (drawer/appbar/tabs), live-updating data ergonomics — built on @archway/valet v0.37.0 heading to 1.0.

**Readiness: 60/100**

valet is genuinely strong for SMALL-to-MEDIUM internal dashboards today and weak for SERIOUS large-data ones. The app-shell story is complete and stable: Surface (fullscreen scroll container + density bridge), AppBar (fixed/portal nav), Drawer (persistent/adaptive, focus-trap, RTL), and Tabs (horizontal/vertical, a11y) — all `status: stable`. Density is a first-class, well-designed system: a global `tight|standard|comfortable` scale (densityScale.ts) plus a `compact` boolean that zeros spacing and cascades across portals (compactContext.ts), wired through Surface to `--valet-space`; components honor it (e.g. Table shrinks hit targets 44px→24px under compact). Forms are well covered: createFormStore + FormControl give submit interception, name-keyed errors, `isSubmitting`/aria-busy, form-wide disable, and focus-first-invalid, with a full field set (TextField, Select single+multiple, Checkbox, Radio, Switch, Slider, Iterator, DateSelector). The Table is a solid mid-size grid: client sort with keyboard-operable sort headers + aria-sort, single/multi selection that survives immutable live refreshes (keyed by getItemKey, Table.tsx:539-574 — a real live-update win), and auto/manual pagination. Live-data ergonomics exist via Snackbar (role=status, pause-on-hover), Progress/LoadingBackdrop, and zustand stores. The 1.0 freeze mechanics are clean for this product: no public `@deprecated` props, and the selection vocabulary is already unified across Table/List/Tree. HOWEVER the data-dense core has hard gaps: (1) ZERO virtualization anywhere — Table renders all rows (mitigated only by 30/page pagination), List renders all items, Tree is explicitly non-virtualized; (2) NO charts/data-viz component or export (fully BYO, with no theming bridge/recipe); (3) Table has no server-side mode (no manual sort/paginate, rowCount, loading, or empty state — it always sorts/paginates the full client array); (4) Table forces `overflow-x:hidden` (no horizontal scroll for wide tables), has no sticky header (no position:sticky in the repo), no column width/resize/pin/reorder API, and no row-detail/expansion; (5) no generic Menu/Popover (no row-action/overflow/context menu) and no Combobox/Autocomplete. Most of these are additive under SemVer so not hard freeze-blockers, but the Table's baked-in layout DEFAULTS (overflow-x:hidden, table-layout:fixed even-width) freeze at 1.0 and are the items most worth resolving before the cut.

### Product blockers

#### 1. Decide & freeze Table's baked-in layout defaults before 1.0 (overflow-x:hidden, table-layout:fixed even widths)

- **Claimed severity:** 🟠 high · **Effort:** M
- **Evidence:** src/components/widgets/Table.tsx:116 (`overflow-x: hidden; /* never allow horizontal scroll */`) and :140 (`table-layout: fixed`). No per-column width API; wide tables wrap via word-break:anywhere at :153.
- **Why it gates 1.0:** These are VISUAL DEFAULTS, not additive props — they freeze at 1.0 under the API/behavior contract. A wide, many-column dashboard table is the most common data-dense case, and today it wraps instead of scrolling with no opt-out. Adding a `scrollX`/`stickyHeader`/column-`width` prop later is additive (fine), but the current default of forcibly suppressing horizontal scroll is a behavior consumers will fight and is awkward to reverse post-freeze. Resolve the intended default now.

#### 2. No large-data strategy: Table/List/Tree are unvirtualized and Table has no server-side mode

- **Claimed severity:** 🟠 high · **Effort:** L
- **Evidence:** src/components/widgets/Table.tsx:739-743 (slices full sorted array) + :909 (maps all rows); src/components/layout/List.tsx:557 (maps all items); src/components/widgets/Tree.meta.json:14 ('Tree is not virtualized'). No loading/empty/manual/rowCount props in Table.
- **Why it gates 1.0:** 'Internal dashboards' implies large datasets; valet today caps out at small/paginated tables. Technically a `virtualized`/`manualPagination`/`rowCount`/`loading` prop is additive (could ship post-1.0 without a break), so this is not a hard SemVer blocker — but it is a blocker for credibly POSITIONING valet for serious dashboards at 1.0. At minimum, ship a sanctioned escape-hatch/recipe (headless rows or a documented react-window integration that inherits theme tokens) so teams aren't stuck.

#### 3. No sticky table header + no empty/loading state for live data

- **Claimed severity:** 🟡 medium · **Effort:** M
- **Evidence:** No `position: sticky` anywhere in src (grep empty); Table height-constrains via maxHeight scroll (Table.tsx:765) with a non-sticky <thead>. Table has no emptyPlaceholder (cf. List.tsx:54) and no loading prop.
- **Why it gates 1.0:** A scrolling data table whose header scrolls out of view is a poor dashboard experience, and a live table that flashes an empty <tbody> on refresh/zero-results looks broken. These can be added as additive props post-1.0, but they are table-stakes for the dashboard use case and worth landing before the 1.0 'terrific' bar.

#### 4. No generic Menu/Popover for row actions and overflow nav

- **Claimed severity:** 🟡 medium · **Effort:** L
- **Evidence:** No menu/popover/combobox component files under src/components and no Menu export in src/index.ts; only SpeedDial (FAB) and Select (form control) exist.
- **Why it gates 1.0:** Row-action menus, column menus, and user/account overflow menus are ubiquitous in dashboards. Additive at 1.0, but its absence forces every consumer to BYO an overlay+focus-managed menu (re-implementing the portal/overlay/focus logic valet already has internally), undercutting the 'terrific' claim for this product.

### Recommendations

#### 3. Theme-mode persistence/system-follow flashes and hydration-mismatches under SSR

- **Claimed severity:** ⬇️ low · **Effort:** M
- **Evidence:** Surface applies theme colors as inline style/CSS vars (src/components/layout/Surface.tsx:213-275); mode is resolved client-side via guarded localStorage/matchMedia (src/system/modePreference.ts:55-79) with a deterministic 'dark' fallback the server uses.
- **Why it gates 1.0:** A marketing site that respects a returning visitor's saved theme or OS preference will render the fallback on the server, then flip on the client — a visible theme flash plus a React inline-style hydration warning. There is no cookie/inline-blocking-script helper. Default (no persistence/system-follow) is mismatch-free, so this is opt-in risk, not a hard blocker — but it directly hits 'polished first paint'.

#### 4. Surface defaults to fixed full-screen app-shell, not document flow

- **Claimed severity:** ⬇️ low · **Effort:** S
- **Evidence:** src/components/layout/Surface.tsx:229-244 (fullscreen=true => position:fixed; inset:0; overflow:auto), default at :58.
- **Why it gates 1.0:** A scrolling, SEO-oriented marketing page wants normal document flow (body scroll, natural sticky headers, long-page scroll-depth analytics). The app-shell default makes an inner div the scroll container; builders must remember fullscreen={false}. Escape hatch exists and works, so this is a docs/default-guidance issue, not a correctness blocker — but it is an easy footgun for this product.

### Recommendations

- **[P0]** Decide and reserve the SSR style-collection architecture before freezing 1.0 — Even if a full getServerStyles ships in 1.1, settle the public shape now: a per-request collector (e.g. a server-side style sheet object that drains renderQueue to a <style> string) plus the isolation mechanism. Adding the export later is non-breaking, but the per-request context (sheet.ts:68 / createStyled.ts:105) and any provider it needs touch the engine surface that 1.0 freezes — so designing it post-freeze risks a breaking retrofit. At minimum, drain renderQueue (not just pendingRules) to ruleText and expose it.
- **[P0]** Ship an SSR/SSG integration guide + recipe (and ideally a scaffold target) — Document the supported path for a marketing site: Next/Astro/Remix wiring, importing @archway/valet/styles.css, Surface fullscreen={false} for document-flow pages, where meta/title/canonical/OG live (framework head), and the current FOUC limitation + workaround until collection lands. Consider a create-valet-app SSG template. Today create-valet-app is SPA-only (createRoot).
- **[P1]** Provide a theme-mode no-flash helper for SSR — Offer a tiny synchronous inline-script snippet (or cookie-driven initial mode) so persistence/system-follow sites set the correct mode before first paint, eliminating the theme flash and the inline-style hydration mismatch on Surface. Document it alongside useInitialTheme's persist/system options.
- **[P1]** Document Surface fullscreen={false} as the marketing/scroll-page default — Make the document-flow recipe prominent (long landing pages, sticky brand nav relative to document, scroll-depth tracking). Consider a dedicated marketing layout example. The app-shell default is right for dashboards/games but wrong-by-default for this product.
- **[P2]** Add marketing component recipes (Hero / Footer / CTA section) — Heroes, footers, and CTA bands are composed from Stack/Box/Panel/Typography/Image/Button today with no canonical pattern. Publish copy-paste recipes (and/or thin presets via definePreset) so brand sites get polished sections fast and consistently.
- **[P2]** Strengthen responsive image guidance (art direction / optional CDN loader hook) — Image already nails CLS/LCP basics but offers only raw srcSet/sizes passthrough. Document responsive/art-direction patterns; consider an optional loader/src-transform hook so teams can plug a CDN optimizer without leaving valet's Image.
- **[P3]** Ship a minimal global reset/normalize guidance with styles.css — styles.css carries only :root token fallbacks (no box-sizing/margin reset). For pixel-tight marketing pages, document the expected reset (or add an opt-in reset entry) so first paint outside Surface is predictable across browsers.
